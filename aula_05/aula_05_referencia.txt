1. QUAL É O PROBLEMA DA AULA 5?
-------------------------------

Na Aula 4, criamos um chat local baseado em texto.

Na Aula 5, queremos que o modelo compreenda mais de uma modalidade.

Exemplos:

- anexar uma foto e perguntar o que aparece nela;
- anexar um gráfico e pedir uma interpretação;
- anexar um áudio e pedir um resumo;
- anexar uma imagem e fazer uma pergunta específica;
- conversar somente por texto, sem arquivo.

Além disso, o modelo da sessão trabalha com saída em inglês.

A aplicação precisa entregar o resultado final em português.

O sistema completo deve:

1. verificar se as APIs existem;
2. verificar o par de tradução inglês-português;
3. verificar o detector de idioma;
4. verificar texto, imagem e áudio no LanguageModel;
5. esperar um gesto antes de iniciar downloads;
6. criar os três recursos;
7. transformar o arquivo em formato aceito;
8. montar uma mensagem multimodal;
9. receber a resposta progressivamente;
10. detectar seu idioma;
11. traduzir quando necessário;
12. permitir cancelamento;
13. mostrar mensagens úteis.


2. O QUE É MULTIMODALIDADE?
---------------------------

Modalidade é o tipo de informação processada.

Exemplos:

texto:
    palavras e frases;

imagem:
    pixels e informação visual;

áudio:
    ondas sonoras, fala, música ou ruídos;

vídeo:
    sequência de imagens e, normalmente, áudio.

Um sistema multimodal combina duas ou mais modalidades.

Nesta aula:

entrada:
    texto obrigatório;
    imagem opcional;
    áudio opcional;

saída:
    texto.

4. TRÊS APIS DE IA
------------------

O projeto utiliza três APIs integradas ao Chrome.

LANGUAGEM

    LanguageModel

Responsabilidade:

- compreender a pergunta;
- analisar texto, imagem ou áudio;
- gerar a resposta.

TRADUÇÃO

    Translator

Responsabilidade:

- traduzir texto de inglês para português.

DETECÇÃO

    LanguageDetector

Responsabilidade:

- classificar o idioma provável de um texto.

Não são três chamadas ao mesmo objeto.

Cada API representa uma tarefa e pode depender de modelos ou pacotes diferentes.


5. MODELO FUNDACIONAL E MODELOS ESPECIALISTAS
---------------------------------------------

O LanguageModel utiliza um modelo fundacional generativo.

Ele realiza tarefas abertas:

- responder;
- explicar;
- interpretar;
- descrever;
- raciocinar sobre a entrada.

Translator e LanguageDetector usam modelos especializados.

Um modelo especialista é otimizado para uma tarefa delimitada.

Tradutor:
    recebe texto em um idioma e gera texto em outro;

Detector:
    recebe texto e ranqueia idiomas prováveis.

Uma arquitetura pode combinar um modelo geral com modelos especializados.


6. POR QUE TRADUZIR DEPOIS DA GERAÇÃO?
--------------------------------------

A sessão declara:

    entrada textual em inglês;
    saída textual em inglês.

Depois, a aplicação traduz o resultado para português.

Essa estratégia cria um pipeline:

    modelo principal
            |
            v
    resposta em idioma suportado
            |
            v
    tradutor especializado
            |
            v
    idioma da interface

Vantagens:

- respeita idiomas suportados pelo modelo principal;
- usa uma API especializada em tradução;
- separa geração e localização;
- permite trocar o idioma final no futuro.

Desvantagens:

- aumenta o tempo total;
- adiciona outro download;
- pode introduzir pequenas mudanças de significado;
- precisa tratar falha de tradução.

16. INPUT FILE OCULTO
---------------------

O input nativo usa:

Um botão visual chama:

Assim:

- mantemos a seleção de arquivos do navegador.


17. PREVIEW DE IMAGEM
---------------------

Quando o arquivo é uma imagem:

1. View cria um elemento img;
2. chama URL.createObjectURL(file);
3. atribui a URL temporária ao src;
4. adiciona uma classe;
5. insere a imagem no preview.

Object URL evita converter toda a imagem para Base64 apenas para visualizar.

Melhoria futura:

Ao remover ou substituir o arquivo, chamar:

    URL.revokeObjectURL(...)

Isso libera a URL temporária.


18. PREVIEW DE ÁUDIO
--------------------

Quando o arquivo é áudio:

1. View cria um elemento audio;
2. usa URL.createObjectURL(file);
3. ativa controls;
4. insere o player.

A pessoa pode conferir o arquivo antes de enviá-lo ao modelo.


19. REMOÇÃO DO ARQUIVO
----------------------

O botão Remover:

- limpa o valor do input;
- limpa o preview;
- remove o nome;
- remove a classe selected.

Isso garante que getFile() não devolva o arquivo removido.


20. MIME TYPE
-------------

MIME type descreve o tipo de mídia.

Exemplos:

    image/png
    image/jpeg
    audio/mpeg
    audio/wav

O código executa:

    file.type.split('/')[0]

Resultado:

    image/png  -> image
    audio/mpeg -> audio

Somente image e audio são adicionados ao prompt.


21. ARRAYBUFFER E BLOB
----------------------

O arquivo selecionado é lido com:

    await file.arrayBuffer()

ArrayBuffer representa bytes brutos na memória.

Depois:

    new Blob([arrayBuffer], { type: file.type })

Blob representa dados binários com um tipo de mídia.

Fluxo:

File
    |
    v
ArrayBuffer
    |
    v
Blob tipado
    |
    v
conteúdo multimodal

File já é um tipo de Blob no navegador. A conversão explícita preserva a intenção
didática e garante um objeto binário com o MIME declarado.

23. DISPONIBILIDADE E CAPACIDADE
--------------------------------

availability não pergunta apenas:

    "Existe algum modelo?"

Ela pergunta:

    "Existe suporte para estas opções?"

O resultado depende de:

- idioma;
- entrada de imagem;
- entrada de áudio;
- saída;
- hardware;
- versão do Chrome;
- downloads;
- políticas.

Estados atuais:

available:
    pronto;

downloadable:
    precisa baixar componentes;

downloading:
    download em andamento;

unavailable:
    configuração não suportada.


24. VERIFICAÇÃO DE REQUISITOS
-----------------------------

checkRequirements() verifica:

1. indicação de Chrome;
2. existência de LanguageModel;
3. existência de Translator;
4. disponibilidade de inglês para português;
5. existência de LanguageDetector;
6. disponibilidade do detector;
7. disponibilidade multimodal do LanguageModel.

Somente unavailable é tratado como falha definitiva.

downloadable e downloading não são erros.

Nesses estados, a aplicação espera o clique.

26. ERRO ENCONTRADO NA INICIALIZAÇÃO
------------------------------------

O console mostrou:

    Error initializing translation:
    NotAllowedError:
    Requires a user gesture when availability is
    "downloading" or "downloadable".

Pilha aproximada:

    TranslationService.initialize()
            |
            v
    Translator.create()
            |
            v
    main()

A página carregava e main() chamava:

    await translationService.initialize()

initialize() chamava Translator.create().

Não existia clique, tecla ou toque associado.

O Chrome recusou iniciar o download.


27. POR QUE O CHROME EXIGE UM GESTO?
------------------------------------

Modelos e pacotes de idioma ocupam armazenamento e consomem rede.

Sem a regra, uma página poderia iniciar downloads automaticamente ao ser aberta.

O gesto demonstra intenção.

Exemplos:

- clique;
- toque;
- tecla;
- submit do formulário.

REGRA

Quando availability retorna downloadable ou downloading, create() deve nascer de
uma interação válida.


28. O PROBLEMA EXISTIA EM MAIS DE UM LUGAR
------------------------------------------

Translator.create() era chamado no load.

LanguageModel.create() também podia ser chamado dentro de checkRequirements()
quando o estado era downloadable.

Portanto, corrigir somente o tradutor esconderia o primeiro erro, mas o modelo de
linguagem poderia falhar depois.

A correção completa removeu todas as criações automáticas.


29. CORREÇÃO NO INDEX.JS
------------------------

index.js não inicializa mais Translator e LanguageDetector durante o load.

Ele:

- cria os objetos;
- verifica recursos;
- configura a tela;
- registra os eventos.

Um comentário registra por que initialize() não fica ali.

Isso preserva a decisão para consultas futuras.


30. CORREÇÃO NO CHECKREQUIREMENTS
---------------------------------

checkRequirements() continua chamando availability().

Ele não chama create().

Para downloadable:

- registra que o modelo será baixado após Enviar;
- não adiciona erro;
- permite a inicialização da interface.

Para downloading:

- informa que a preparação ocorrerá após o clique;
- não bloqueia.

Para unavailable:

- adiciona erro;
- impede o uso incompatível.


31. CORREÇÃO NO SUBMIT
----------------------

handleSubmit() é executado a partir do evento submit.

Antes do primeiro await, ele inicia:

    translationService.initialize()

e:

    aiService.createSession()

Assim, as chamadas create() nascem dentro do clique.

Depois:

    Promise.all(...)

aguarda os recursos.


32. POR QUE INICIAR ANTES DO PRIMEIRO AWAIT?
--------------------------------------------

Uma função async executa sincronamente até encontrar o primeiro await.

Se fizermos:

    await prepararTradutor()
    await prepararModelo()

a segunda operação começará muito depois do evento original.

No código corrigido:

    const translationInitialization = ...
    const aiSessionCreation = ...

    await Promise.all([...])

As duas operações são iniciadas imediatamente.

TranslationService também cria as Promises do Translator e LanguageDetector antes
de aguardar.


33. PROMISE.ALL
---------------

Promise.all recebe várias Promises.

Ele:

- inicia tarefas independentes;
- espera todas;
- devolve os resultados na ordem fornecida;
- rejeita se uma delas falhar.

Na aula:

    [inicialização da tradução, stream da IA]

Os resultados são desestruturados:

    const [, aiResponseChunks] = ...

O primeiro resultado é apenas true.

O segundo é o stream que será consumido.


34. INICIALIZAÇÃO IDEMPOTENTE
-----------------------------

TranslationService.initialize() começa verificando:

    this.translator && this.languageDetector

Se ambos já existem, retorna sem recriar.

Isso torna o método idempotente para o caso comum:

    chamar novamente não repete o trabalho já concluído.

Benefícios:

- evita downloads repetidos;
- evita instâncias desnecessárias;
- reduz latência nas perguntas seguintes.


35. DOWNLOAD EM PARALELO
------------------------

TranslationService cria:

    translatorPromise
    detectorPromise

antes do await.

Depois usa Promise.all.

O tradutor e o detector podem ser preparados paralelamente.

Se uma instância já existe:

    Promise.resolve(instancia)

é usada.

Assim, uma tentativa parcial pode reutilizar o recurso pronto.


36. PROGRESSO DOS DOWNLOADS
---------------------------

Cada create() recebe monitor().

Monitor registra:

    downloadprogress

Recursos acompanhados:

- modelo de linguagem;
- tradutor inglês-português;
- detector de idioma.

As mensagens são encaminhadas por callback:

    onProgress(mensagem)

O service não acessa diretamente o DOM.

O controller converte o callback em:

    view.setOutput(mensagem)


37. CÁLCULO COMPATÍVEL DE PORCENTAGEM
-------------------------------------

Versões diferentes podem oferecer:

- loaded como fração de zero a um;
- loaded e total.

O código trata os dois formatos:

se total existe:

    loaded / total * 100

senão:

    loaded * 100

Depois:

    toFixed(0)

gera uma porcentagem inteira para a interface.


38. LANGUAGE DETECTOR
---------------------

Depois da geração:

    languageDetector.detect(text)

retorna uma lista ranqueada.

O primeiro item representa o idioma mais provável.

O código lê:

    detectionResults[0]?.detectedLanguage

Optional chaining evita falha se:

- lista estiver vazia;
- primeiro item não existir.


39. POR QUE DETECTAR ANTES DE TRADUZIR?
--------------------------------------

Se a resposta já estiver em português, traduzir novamente seria:

- desnecessário;
- mais lento;
- sujeito a alteração;
- desperdício de recursos.

O fluxo é:

idioma detectado = pt
    |
    v
retorna texto original

idioma diferente
    |
    v
traduz para português


40. TRANSLATOR
--------------

Translator é criado com:

sourceLanguage:
    en;

targetLanguage:
    pt.

Esses códigos seguem BCP 47.

O tradutor é específico para o par.

Se quisermos espanhol para português, precisaríamos criar outra configuração:

    sourceLanguage: 'es'
    targetLanguage: 'pt'


41. TRADUÇÃO EM STREAMING
-------------------------

O projeto usa:

    translateStreaming(text)

O stream é percorrido com:

    for await

Na implementação da aula, cada chunk representa a tradução acumulada.

Por isso:

    translated = chunk

substitui o valor anterior.

Se uma versão entregar somente deltas, o contrato precisará ser revisto.


42. FALLBACK DA TRADUÇÃO
------------------------

Se translator não existir:

- registra warning;
- retorna o texto original.

Se detect ou translate falhar:

- registra o erro;
- retorna o texto original.

Isso é graceful degradation.

A geração principal continua útil mesmo que a tradução falhe.


43. SESSÃO DO LANGUAGEMODEL
---------------------------

createSession():

1. aborta operação anterior;
2. cria AbortController;
3. destrói sessão anterior;
4. monta sessionOptions;
5. cria LanguageModel;
6. monta conteúdo;
7. adiciona arquivo;
8. inicia promptStreaming;
9. devolve o stream.

A sessão anterior não é reutilizada.

Cada pergunta começa um contexto novo.


44. SYSTEM PROMPT MULTIMODAL
----------------------------

O initialPrompts possui role system.

Seu conteúdo é uma lista com item:

    type: text
    value: instrução

Ele pede:

- resposta clara;
- resposta objetiva;
- texto simples;
- ausência de Markdown.

No formato multimodal, content pode representar uma coleção de partes.


45. CONTEÚDO DO USUÁRIO
-----------------------

contentArray começa com:

    { type: "text", value: question }

Se há arquivo:

    { type: "image", value: blob }

ou:

    { type: "audio", value: blob }

Exemplo:

content:
    parte 1 -> pergunta em texto;
    parte 2 -> imagem.

O modelo recebe as partes na mesma mensagem de papel user.


46. PERGUNTA E ARQUIVO TRABALHAM JUNTOS
---------------------------------------

O arquivo não define sozinho a tarefa.

A pergunta orienta o que fazer.

Exemplos:

Imagem:

    "Descreva os objetos principais."

    "Existe algum risco visível?"

    "Leia o texto presente."

Áudio:

    "Resuma o assunto."

    "Qual é o tom da fala?"

    "Liste os pontos mencionados."

Quanto mais específica a pergunta, mais útil tende a ser a resposta.


47. PROMPTSTREAMING
-------------------

promptStreaming permite receber texto progressivamente.

O controller percorre:

    for await (const chunk of aiResponseChunks)

Para cada trecho:

- verifica cancelamento;
- registra no console;
- acumula em fullResponse;
- atualiza a tela.


48. RESPOSTA PARCIAL E RESPOSTA FINAL
-------------------------------------

Durante a geração, a tela mostra o inglês recebido.

Ao concluir:

    Traduzindo resposta...

Depois substitui pelo português.

Isso fornece feedback imediato.

Uma alternativa futura seria:

- mostrar duas áreas;
- manter original em inglês;
- mostrar tradução abaixo;
- permitir alternar idiomas.


49. DELTA VERSUS CONTEÚDO ACUMULADO
-----------------------------------

Streams podem seguir dois contratos.

DELTA

    "The"
    " image"
    " shows"

Uso:

    fullResponse += chunk

ACUMULADO

    "The"
    "The image"
    "The image shows"

Uso:

    fullResponse = chunk

O LanguageModel da versão usada deve ser confirmado.

O projeto usa concatenação para a geração e substituição para a tradução.


50. ABORTCONTROLLER
-------------------

AIService cria:

    new AbortController()

O signal é entregue a promptStreaming.

Ao clicar Parar:

    aiService.abort()

chama:

    abortController.abort()

O controller deixa de consumir novos chunks.


51. ESTADO DO BOTÃO
-------------------

FormController mantém:

    isGenerating

Quando true:

- texto do botão vira Parar;
- classe stop-button é adicionada.

Quando false:

- texto vira Enviar;
- classe é removida.

O mesmo submit decide:

se está gerando:
    parar;

se não está:
    enviar.


52. TRATAMENTO DE ERROS NO CONTROLLER
-------------------------------------

handleSubmit() usa try e catch.

Em erro:

- registra a exceção completa;
- aborta a geração;
- mostra uma mensagem.

Depois:

- devolve o botão ao estado Enviar.

A mensagem de TranslationService inclui error.message original para facilitar
diagnóstico.


53. PARÂMETROS DE AMOSTRAGEM
----------------------------

A interface explica:

temperature:
    criatividade e variedade;

topK:
    quantidade de candidatos prováveis.

Entretanto, a Prompt API web atual pode não expor números crus.

O código não presume mais:

    LanguageModel.params()


54. FEATURE DETECTION PARA PARAMS
---------------------------------

getParams() verifica:

    typeof LanguageModel.params === 'function'

Se existir:

- consulta parâmetros;
- ativa supportsSamplingParameters;
- usa limites reais.

Se não existir:

- retorna fallback;
- mantém a aula visível;
- não envia temperature e topK;
- desativa os campos.


55. FALLBACK DE PARÂMETROS
--------------------------

Valores de fallback:

    defaultTemperature: 1
    defaultTopK: 3
    maxTemperature: 2
    maxTopK: 128

Eles inicializam a interface.

Não significam que a API atual aceita esses números.

sessionOptions recebe temperature e topK somente quando:

    supportsSamplingParameters === true


56. CAMPOS DESATIVADOS COM EXPLICAÇÃO
-------------------------------------

View.setSamplingParametersAvailability() desativa os campos quando necessário.

Os controles continuam visíveis para preservar:

- comparação com a aula;
- explicação de amostragem;
- compatibilidade com versões legadas.

O atributo title informa:

    Parâmetro legado indisponível nesta versão do Chrome.


57. POR QUE A API MUDOU?
-----------------------

APIs experimentais evoluem.

Parâmetros numéricos nem sempre têm significado uniforme em modelos diferentes.

Uma plataforma pode preferir:

- valores padrão;
- modos descritivos;
- configurações limitadas;
- parâmetros liberados por experimento.

Lição:

O código deve tratar a capacidade real, não apenas reproduzir uma versão antiga
da documentação.

-------------------------

Em produção:

- limite tamanho;
- valide MIME;

- evite executar conteúdo;
- proteja previews;
- libere Object URLs;
- aplique timeout;

69. LIMITES DE ENTRADA
----------------------

Arquivos grandes podem:

- consumir memória;
- aumentar latência;
- exceder limites;
- falhar;
- travar a experiência.

Melhorias:

- máximo de MB;
- máximo de duração;
- máximo de dimensões;
- compressão de imagem;
- aviso antes do envio;
- recusa amigável.


70. ENTRADA DE ÁUDIO E GPU
--------------------------

Áudio pode exigir suporte mais forte de hardware.

Uma máquina que responde texto pode não aceitar áudio.

Por isso:

- capabilities incluem audio;
- availability usa as mesmas opções;
- unavailable deve ser explicado.

Uma melhoria seria verificar capacidades dinamicamente e desativar apenas a
modalidade ausente.


71. TRATAMENTO POR MODALIDADE
-----------------------------

Hoje, getSessionCapabilities() sempre declara:

- texto;
- imagem;
- áudio.

Alternativa futura:

Sem arquivo:
    pedir somente texto;

Com imagem:
    pedir texto + imagem;

Com áudio:
    pedir texto + áudio.

Benefícios:

- compatibilidade maior;
- menos requisitos;
- diagnóstico preciso;
- suporte parcial.


72. CONCORRÊNCIA
----------------

Promise.all é usado para preparação independente.

Isso não significa iniciar várias perguntas ao mesmo tempo.

FormController mantém uma geração ativa.

Se Enviar for acionado durante geração:

- comportamento muda para Parar.

Uma aplicação multiusuário precisaria:

- sessões separadas;
- filas;
- limites;
- isolamento de contexto.


73. CICLO DE VIDA
-----------------

LanguageModel:

- sessão anterior destruída a cada pergunta;
- geração anterior abortada.

Translator:

- instância mantida;
- reutilizada.

LanguageDetector:

- instância mantida;
- reutilizada.

Essa diferença existe porque:

- conversa precisa de contexto isolado;

FormController:
