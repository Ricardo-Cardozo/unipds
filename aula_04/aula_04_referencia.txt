1. QUAL É O PROBLEMA DA AULA 4?
-------------------------------

Nas aulas anteriores, usamos inteligência artificial para:

- classificar e recomendar produtos;
- detectar objetos em imagens;
- transformar previsões em ações dentro de um jogo.

Na Aula 4, o problema muda.

Agora queremos permitir que uma pessoa faça uma pergunta em linguagem natural e
receba uma resposta gerada por um modelo de linguagem.

O desafio não é somente chamar o modelo.

O sistema completo precisa:

1. descobrir se o navegador oferece a API;
2. descobrir se a máquina suporta o modelo;
3. descobrir se o modelo já está instalado;
4. solicitar o download no momento permitido;
5. criar uma sessão;
6. enviar o prompt;
7. receber o texto aos poucos;
8. mostrar o progresso na interface;
9. permitir o cancelamento;
10. tratar incompatibilidades e erros.


2. O QUE É IA GENERATIVA?
-------------------------

IA generativa é uma categoria de sistemas capazes de produzir conteúdo novo.

Dependendo do modelo, esse conteúdo pode ser:

- texto;
- imagem;
- áudio;
- vídeo;
- código;
- dados estruturados.

Nesta aula, trabalhamos com geração de texto.

A aplicação recebe uma pergunta e produz uma resposta textual.

Exemplo conceitual:

entrada:
    "Explique o que é uma rede neural."

saída:
    texto gerado pelo modelo para responder à pergunta.


3. O QUE É UM MODELO DE LINGUAGEM?
----------------------------------

Um modelo de linguagem aprende padrões existentes em grandes quantidades de
texto.

Durante a geração, ele estima quais tokens são mais adequados para continuar o
contexto recebido.

Um token pode representar:

- uma palavra;
- parte de uma palavra;
- pontuação;
- símbolos;
- espaços ou combinações de caracteres.

De forma simplificada:

prompt
    |
    v
modelo calcula probabilidades
    |
    v
seleciona o próximo token
    |
    v
adiciona o token ao contexto
    |
    v
repete até concluir

O modelo não consulta uma resposta pronta em um banco de frases. Ele gera a
sequência com base no contexto e nos padrões aprendidos.


4. O QUE É GEMINI NANO?
-----------------------

Gemini Nano é uma versão compacta da família Gemini, preparada para executar em
dispositivos locais compatíveis.

No contexto desta aula, ele é administrado pelo Chrome.

Isso significa que a aplicação não baixa manualmente um arquivo de pesos e não
implementa o motor de inferência.

O navegador cuida de:

- verificar compatibilidade;
- obter os componentes necessários;
- baixar o modelo;
- armazenar o modelo;
- criar a sessão;
- executar a inferência;
- expor o resultado por uma API JavaScript.

O código da aplicação conversa com a interface LanguageModel.


5. MODELO LOCAL E MODELO NA NUVEM
---------------------------------

MODELO NA NUVEM

    |

Vantagens:

Desvantagens:

    |

Vantagens:

- baixa latência depois do download;
- possibilidade de uso sem conexão após a instalação;
- não exige enviar cada prompt para um servidor;
- não expõe uma chave de API no frontend;
- melhora a privacidade para determinados casos.

Desvantagens:

- depende do navegador;
- depende do hardware;
- exige espaço em disco;
- o primeiro download pode ser grande;
- modelos locais menores têm limitações;
- APIs experimentais podem mudar.


6. O QUE SIGNIFICA BUILT-IN AI?
-------------------------------

Built-in AI significa inteligência artificial integrada à plataforma.

Neste projeto, o navegador fornece uma API de alto nível.

Em vez de o projeto implementar:

- carregamento de pesos;
- alocação de GPU;
- tokenização;
- inferência;
- cache do modelo;
- atualização dos arquivos;

o JavaScript usa:

    LanguageModel.availability(...)

    LanguageModel.create(...)

    session.promptStreaming(...)

Essa abstração reduz a complexidade da aplicação, mas cria dependência da API e
das regras definidas pelo navegador.


7. A PROMPT API
---------------

A Prompt API permite criar uma sessão com um modelo de linguagem e enviar
prompts pelo JavaScript.

As operações centrais usadas na aula são:

LanguageModel.availability(opcoes)
    verifica o estado de disponibilidade;

LanguageModel.create(opcoes)
    prepara e cria uma sessão;

session.promptStreaming(mensagem, opcoes)
    gera uma resposta em streaming;

session.destroy()
    encerra uma sessão que não será mais utilizada.

A API ainda evolui. Por isso, o código precisa fazer detecção de recursos e não
presumir que toda versão do Chrome possui exatamente os mesmos métodos.

10. POR QUE TYPE="MODULE" IMPORTA?
---------------------------------

Scripts do tipo module seguem regras mais rígidas de origem e segurança.

Eles também permitem:

- import e export;
- escopo próprio;
- carregamento assíncrono por padrão;
- organização moderna de código.

Entretanto, abrir o HTML diretamente como arquivo local gera uma origem especial.

O endereço começa com:

    file://

Nesse cenário, o navegador tratou a origem como:

    null

Por segurança, o Chrome bloqueou o carregamento de index.js.


11. PRIMEIRO ERRO: FILE, CORS E ORIGIN NULL
-------------------------------------------

O erro exibido foi equivalente a:

    Access to script at 'file:///.../index.js'
    from origin 'null' has been blocked by CORS policy

E também:

    GET file:///.../index.js net::ERR_FAILED

CAUSA

O index.html foi aberto diretamente pelo gerenciador de arquivos.

Assim:

    index.html -> file://
    index.js   -> file://
    origem     -> null

Como index.js é um módulo, o Chrome exige uma origem válida.

CORS significa Cross-Origin Resource Sharing.

É o mecanismo que determina quando um recurso de uma origem pode ser lido por
outra origem.

Mesmo que os dois arquivos estejam na mesma pasta, file não equivale a um
servidor web normal.


12. CORREÇÃO: USAR UM SERVIDOR HTTP LOCAL
-----------------------------------------

A solução é servir a pasta por HTTP.

Comandos:

    cd "/home/ricardo/Área de trabalho/unipds/machine_learning/aula_04"
    npm install
    npm start

O script start executa:

    npx http-server .

Então o acesso passa a acontecer por um endereço parecido com:

    http://127.0.0.1:8080

ou, se a porta 8080 já estiver ocupada:

    http://127.0.0.1:8081

Agora a página possui uma origem HTTP válida e o módulo pode ser carregado.

REGRA PARA LEMBRAR

Projetos com modules, fetch, workers e várias APIs modernas devem ser abertos por
um servidor HTTP, mesmo durante o desenvolvimento local.

22. LIMITAÇÃO DE IDIOMA ENCONTRADA
----------------------------------

O console do Chrome exibiu um aviso pedindo a definição do idioma de saída.

Na versão testada, o próprio aviso informou suporte oficial de saída para:

- de;
- en;
- es;
- fr;
- ja.

Português não estava nessa lista oficial.

Isso significa que pedir:

    expectedOutputLanguages: ['pt']

pode resultar em indisponibilidade ou erro, mesmo que o modelo algumas vezes
entenda ou produza português.

Boas estratégias:

1. usar um idioma oficialmente suportado;
2. manter português somente quando a versão instalada confirmar suporte;
3. oferecer fallback para uma API em nuvem;
4. mostrar uma mensagem clara ao usuário;
5. não confundir capacidade ocasional com suporte garantido.

O system prompt pede resposta em português, mas o prompt não substitui o suporte
formal de idioma da API.


23. AVAILABILITY: O ESTADO DO MODELO
------------------------------------

A chamada:

    LanguageModel.availability(languageOptions)

consulta se a combinação solicitada pode ser usada.

Estados principais:

available
    modelo pronto para uso;

downloadable
    modelo ou componente pode ser baixado;

downloading
    download está em andamento;

unavailable
    recurso não pode ser usado naquele ambiente ou com aquelas opções.

Esse método não gera texto.

Ele ajuda a aplicação a decidir qual experiência mostrar antes de criar a
sessão.


24. COMO O CÓDIGO TRATA CADA ESTADO
-----------------------------------

AVAILABLE

- nenhuma mensagem de erro;
- pergunta pode ser processada imediatamente.

DOWNLOADABLE

- informa que o modelo precisa ser baixado;
- altera o texto do botão;
- espera a pessoa clicar em Enviar.

DOWNLOADING

- informa que o download está em andamento;
- orienta a enviar uma pergunta para acompanhar.

UNAVAILABLE

- registra que o dispositivo ou a configuração não oferece suporte;
- o fluxo principal desativa o botão.

Essa separação melhora a experiência porque "ainda não foi baixado" não é o
mesmo que "não é suportado".


25. SEGUNDO ERRO: DOWNLOAD SEM GESTO DO USUÁRIO
-----------------------------------------------

Depois de corrigir o acesso por HTTP, surgiu outro erro:

    NotAllowedError:
    Requires a user gesture when availability is
    "downloading" or "downloadable".

CAUSA

A versão inicial chamava LanguageModel.create() automaticamente durante o
carregamento da página.

Quando o modelo ainda precisa ser baixado, o Chrome exige uma ativação do
usuário.

Exemplos de ativação:

- clique;
- toque;
- tecla;
- envio explícito do formulário.

Essa regra evita que qualquer página inicie silenciosamente um download grande.


26. CORREÇÃO: CRIAR O MODELO DEPOIS DO CLIQUE
---------------------------------------------

O fluxo foi reorganizado.

checkRequirements() agora:

- consulta o estado;
- informa o que está acontecendo;
- não inicia o download automaticamente.

LanguageModel.create() fica dentro de askAI().

askAI() é chamada a partir do submit do formulário.

Portanto:

carregamento da página
    |
    v
apenas verifica disponibilidade
    |
    v
usuário clica em Enviar
    |
    v
evento submit
    |
    v
askAI()
    |
    v
LanguageModel.create()
    |
    v
download autorizado

Esse fluxo respeita a regra do navegador e torna a intenção do usuário explícita.


27. MONITORANDO O DOWNLOAD
--------------------------

LanguageModel.create() recebe uma função monitor.

Ela registra um listener para:

    downloadprogress

O evento fornece dados de progresso.

O código calcula uma porcentagem e mostra:

    Baixando o Gemini Nano: 37%

Benefícios:

- evita a impressão de que a página travou;
- explica por que a primeira resposta demora;
- permite acompanhar um download grande;
- melhora a confiança da pessoa na interface.

O primeiro uso tende a ser o mais demorado.

Depois que o modelo e seus componentes estão instalados, novas sessões podem ser
criadas sem repetir o download completo.

29. INITIALPROMPTS
------------------

O código cria a sessão com um prompt inicial de papel system.

Objetivo da instrução:

- definir o comportamento do assistente;
- pedir clareza;
- pedir objetividade;
- pedir texto simples em vez de Markdown.

Exemplo conceitual:

    role: system

O system prompt não é a pergunta da pessoa.

30. PAPÉIS SYSTEM E USER
------------------------

SYSTEM

Define identidade, regras e estilo esperado.

Exemplos:

- responda com objetividade;
- explique para iniciantes;
- não use Markdown;
- responda em determinado idioma.

USER

Contém a solicitação feita pela pessoa.

No projeto:

    role: 'user'
    content: question

Separar papéis deixa a intenção de cada mensagem explícita para o modelo.

O system prompt deve orientar, mas não garante sozinho:

- que toda informação será verdadeira;
- que o idioma seja formalmente suportado;
- que nunca ocorra alucinação;
- que uma política da plataforma seja contornada.


31. PROMPT NÃO É APENAS UMA PERGUNTA
------------------------------------

Prompt é o contexto fornecido ao modelo para orientar a geração.

Um bom prompt pode conter:

- objetivo;
- contexto;
- formato desejado;
- restrições;
- público-alvo;
- exemplos;
- critérios de qualidade.

Exemplo fraco:

    "Fale sobre JavaScript."

Exemplo mais definido:

    "Explique promises em JavaScript para uma pessoa iniciante.
     Use um exemplo curto e compare com async/await."

Quanto mais clara a intenção, maior a chance de a resposta ser útil.


32. TEMPERATURE
---------------

Temperature controla a aleatoriedade da seleção dos próximos tokens.

Simplificação:

temperature baixa:

- respostas mais previsíveis;
- maior foco nos tokens de alta probabilidade;
- útil para explicações objetivas e tarefas determinísticas.

temperature alta:

- maior variedade;
- respostas potencialmente mais criativas;
- maior possibilidade de fugir do caminho mais provável.

Temperature não significa inteligência.

Também não garante:

- veracidade;
- qualidade;
- criatividade útil;
- ausência de repetição.

Ela altera a distribuição usada na amostragem.


33. TOPK
--------

topK limita quantos candidatos mais prováveis participam da escolha do próximo
token.

Exemplo conceitual:

O modelo calcula centenas de candidatos.

Com topK igual a 3:

- conserva os três mais prováveis;
- descarta os demais;
- seleciona dentro desse pequeno conjunto.

topK menor:

- tende a produzir comportamento mais previsível;

topK maior:

- permite mais variedade.

Temperature e topK podem atuar juntos, mas não são equivalentes.


34. MUDANÇA DA API: PARÂMETROS LEGADOS
--------------------------------------

O material original da aula usa:

    LanguageModel.params()

e envia:

    temperature
    topK

No Chrome testado durante nossa adaptação, esses recursos não estavam
necessariamente disponíveis na API web padrão atual.

Por isso, o código agora testa:

    typeof LanguageModel.params === 'function'

Se o método existir:

- consulta limites e valores padrão;
- ativa supportsSamplingParameters;
- envia temperature e topK para a sessão.

Se não existir:

- usa valores de fallback somente para preencher a interface;
- desativa os controles;
- mantém a explicação pedagógica;
- não envia opções incompatíveis para LanguageModel.create().

Essa técnica é chamada feature detection.


35. FEATURE DETECTION
---------------------

Feature detection significa testar se um recurso existe antes de usá-lo.

Exemplo:

    if (typeof LanguageModel.params === 'function') {
        ...
    }

É melhor do que presumir comportamento apenas pelo número da versão.

Motivos:

- recursos podem ser ativados gradualmente;
- flags podem mudar a disponibilidade;
- perfis diferentes podem ter configurações diferentes;
- APIs experimentais mudam rapidamente;
- extensões e páginas web podem receber superfícies diferentes.

REGRA

Em APIs experimentais, consulte o recurso real em tempo de execução.


36. FALLBACKPARAMS
------------------

O objeto fallbackParams contém:

- defaultTemperature: 1;
- defaultTopK: 3;
- maxTemperature: 2;
- maxTopK: 128.

Ele permite inicializar os campos mesmo sem LanguageModel.params().

Entretanto, esses valores não provam que a versão atual aceitará os parâmetros.

Por isso, o código:

1. mostra os valores;
2. desativa os campos quando a API não suporta;
3. adiciona um title explicativo;
4. registra um aviso no console;
5. não envia os parâmetros à sessão.

O fallback preserva a aula sem fingir suporte inexistente.


37. EVENTOS DOS CONTROLES
-------------------------

O evento input do controle temperature atualiza imediatamente o número mostrado
na tela.

O evento input de topK faz o mesmo.

Fluxo:

usuário move ou altera o campo
    |
    v
evento input
    |
    v
textContent recebe o novo valor

Isso fornece feedback visual instantâneo.

Os listeners são registrados apenas depois da verificação inicial.


38. ENVIO DO FORMULÁRIO
-----------------------

O formulário escuta:

    submit

O código executa:

    event.preventDefault()

Sem isso, o navegador faria o comportamento padrão do formulário, normalmente
recarregando ou navegando a página.

Depois:

- se já está gerando, o clique funciona como Parar;
- se não está gerando, onSubmitQuestion() inicia a pergunta.

Usar submit também permite que a interface funcione com teclado, não apenas com
um listener de click no botão.


39. VALIDAÇÃO DA PERGUNTA
-------------------------

O código lê:

    questionInput.value

Depois verifica:

    question.trim()

Se o resultado estiver vazio, a função retorna.

trim() remove espaços em branco do começo e do fim.

Assim, entradas contendo apenas:

- espaços;
- tabulações;
- quebras de linha;

não iniciam uma geração desnecessária.


40. CONVERSÃO DOS CAMPOS NUMÉRICOS
----------------------------------

Valores de campos HTML chegam como texto.

Por isso, usamos:

    parseFloat(...)

para temperature e:

    parseInt(...)

para topK.

Temperature pode ter decimal, como:

    0.7

topK representa uma quantidade inteira, como:

    3

Mesmo que os controles estejam desativados em uma API moderna, essa conversão
continua documentando o conceito da versão da aula.


41. PROMPT E PROMPTSTREAMING
----------------------------

Existem duas experiências conceituais:

PROMPT

- espera a resposta ser concluída;
- entrega o resultado completo;
- implementação visual mais simples;
- pessoa espera sem ver o texto parcial.

PROMPTSTREAMING

- entrega partes durante a geração;
- permite mostrar a resposta progressivamente;
- melhora a percepção de velocidade;
- combina bem com cancelamento.

Nesta aula usamos:

    session.promptStreaming(...)


42. O QUE É STREAMING?
----------------------

Streaming significa processar dados conforme eles ficam disponíveis.

Sem streaming:

pergunta
    |
    v
espera toda a geração
    |
    v
mostra a resposta completa

Com streaming:

pergunta
    |
    v
primeiro trecho -> tela
    |
    v
segundo trecho -> tela
    |
    v
terceiro trecho -> tela
    |
    v
fim

O tempo total pode ser semelhante, mas o tempo até o primeiro conteúdo visível é
menor.


43. ASYNC GENERATOR
-------------------

askAI é uma função geradora assíncrona.

Ela combina:

- async;
- generator;
- yield.

Sua responsabilidade é:

1. preparar o cancelamento;
2. destruir a sessão anterior;
3. montar opções;
4. criar a sessão;
5. iniciar promptStreaming;
6. percorrer o stream;
7. entregar cada trecho com yield.

Em vez de retornar toda a resposta uma vez, a função produz valores ao longo do
tempo.


44. YIELD
---------

yield pausa temporariamente a função geradora e entrega um valor ao consumidor.

No projeto:

    yield chunk

Cada chunk é uma parte da resposta.

Depois que o consumidor pede o próximo valor, a execução continua de onde parou.

Esse modelo é adequado para:

- streams;
- paginação;
- eventos assíncronos;
- leitura progressiva;
- sequências cujo tamanho não é conhecido antecipadamente.


45. FOR AWAIT
-------------

onSubmitQuestion() consome a resposta com:

    for await (const chunk of aiResponseChunks)

for await:

- espera cada item assíncrono;
- executa o corpo do laço;
- solicita o próximo item;
- termina quando o stream termina.

O primeiro chunk remove a mensagem "Processando".

Depois, cada trecho é acrescentado com:

    output.textContent += chunk


46. CUIDADO: CHUNK PODE SER DELTA OU ACUMULADO
----------------------------------------------

Uma API de streaming pode entregar:

DELTA

Cada chunk contém apenas a nova parte.

Exemplo:

    "Olá"
    ", "
    "mundo"

Nesse caso, concatenar funciona:

    output.textContent += chunk

ACUMULADO

Cada chunk contém toda a resposta produzida até aquele ponto.

Exemplo:

    "Olá"
    "Olá, "
    "Olá, mundo"

Nesse caso, concatenar repetiria texto. O correto seria substituir:

    output.textContent = chunk

Ao atualizar a API ou o navegador, é importante confirmar o contrato atual de
promptStreaming.


47. ABORTCONTROLLER
-------------------

AbortController é uma API do navegador para cancelar operações assíncronas que
aceitam um AbortSignal.

O projeto cria:

    new AbortController()

e envia:

    signal: aiContext.abortController.signal

para promptStreaming.

Quando a pessoa clica em Parar:

    aiContext.abortController.abort()

O signal passa para o estado aborted e a operação pode ser encerrada.


48. POR QUE CANCELAMENTO É IMPORTANTE?
--------------------------------------

Sem cancelamento:

- uma resposta longa continua consumindo recursos;
- o botão Parar seria apenas visual;
- uma nova pergunta poderia concorrer com a anterior;
- a interface poderia receber trechos antigos;
- a pessoa perderia controle da experiência.

Antes de iniciar outra geração, o código também aborta o controlador anterior.

Isso reduz o risco de duas respostas atualizarem a mesma área ao mesmo tempo.


49. BOTÃO ENVIAR E PARAR
------------------------

A função toggleSendOrStopButton altera o estado do botão.

AO INICIAR

- isGenerating recebe true;
- texto vira "Parar";
- classe stop-button é adicionada;
- botão recebe aparência vermelha.

AO ENCERRAR

- aborta uma operação restante;
- isGenerating recebe false;
- texto volta para "Enviar";
- classe stop-button é removida.

Um único botão representa duas ações dependendo do estado atual.


50. CICLO DE VIDA DA SESSÃO
---------------------------

Antes de criar uma nova sessão:

    aiContext.session.destroy()

Isso encerra a sessão anterior.

Fluxo atual:

pergunta 1
    |
    v
cria sessão A
    |
    v
gera resposta
    |
    v
pergunta 2
    |
    v
destrói sessão A
    |
    v
cria sessão B

Consequência importante:

O projeto atual não mantém uma conversa de múltiplos turnos entre perguntas.

Cada envio começa com uma nova sessão e o mesmo system prompt.


51. COMO CRIAR MEMÓRIA DE CONVERSA NO FUTURO
--------------------------------------------

Para manter contexto entre perguntas, seria possível:

- reutilizar a mesma sessão;
- armazenar histórico de mensagens;
- limitar o tamanho do histórico;
- resumir mensagens antigas;
- mostrar um botão "Nova conversa";
- destruir a sessão somente quando a conversa for encerrada.

Cuidados:

- sessões têm limite de contexto;
- históricos grandes consomem mais recursos;
- informações antigas podem influenciar respostas novas;
- dados sensíveis não devem ser mantidos sem necessidade;
- é necessário mostrar à pessoa quando existe memória.


52. TRATAMENTO DE ERROS
-----------------------

onSubmitQuestion() usa:

    try
    catch
    finally

TRY

- cria o generator;
- percorre os chunks;
- atualiza a saída.

CATCH

- ignora AbortError como cancelamento esperado;
- registra outros erros no console;
- mostra uma mensagem amigável.

FINALLY

- sempre devolve o botão ao estado Enviar.

finally é importante porque também executa quando:

- a geração conclui;
- ocorre uma falha;
- acontece uma exceção;
- a operação é interrompida.


53. ABORTERROR NÃO É UMA FALHA COMUM
------------------------------------

Quando a pessoa clica voluntariamente em Parar, a rejeição pode ter:

    error.name === 'AbortError'

Isso representa uma ação esperada.

Mostrar uma mensagem vermelha de erro para um cancelamento voluntário prejudicaria
a experiência.

Por isso, o código diferencia:

cancelamento:
    silencioso e esperado;

outro erro:
    registrado e mostrado.


54. TEXTCONTENT E INNERHTML
---------------------------

As respostas do modelo são inseridas com:

    textContent

Isso é importante porque o conteúdo é tratado como texto, não como HTML.

Se o modelo gerar:

    <script>...</script>

textContent mostra os caracteres e não executa a tag.

O código usa innerHTML apenas para montar as mensagens internas de requisitos com
quebras <br>.

REGRA DE SEGURANÇA

Conteúdo vindo do usuário, do modelo ou de uma API externa não deve ser inserido
diretamente com innerHTML sem sanitização.


55. MENSAGENS DE ESTADO
-----------------------

A interface informa:

- processando a pergunta;
- preparando o Gemini Nano;
- necessidade de download;
- progresso do download;
- incompatibilidade;
- erro na geração.

Mensagens de estado são parte da funcionalidade.

Uma operação assíncrona sem feedback parece travada, mesmo quando está funcionando.

Uma boa interface deve responder:

1. o clique foi recebido?
2. o que está acontecendo?
3. ainda está trabalhando?
4. houve erro?
5. o que a pessoa deve fazer agora?


56. PRIVACIDADE DA EXECUÇÃO LOCAL
---------------------------------

Depois que os componentes necessários estão instalados, a inferência do modelo
integrado ocorre no dispositivo.

Isso permite que o conteúdo da pergunta não precise ser enviado a uma API remota
para gerar cada resposta.

Benefícios possíveis:

- dados permanecem no dispositivo durante a inferência;
- menor exposição pela rede;
- não há chave secreta de um provedor no frontend;
- uso pode continuar sem internet após os recursos estarem disponíveis.

Ainda existem responsabilidades da aplicação:

- não registrar prompts sensíveis sem necessidade;
- não enviar conteúdo a serviços de analytics indevidos;
- explicar o que é local e o que não é;
- proteger dados salvos no navegador;
- não prometer privacidade além do comportamento real do sistema.

O fato de o modelo ser local não torna automaticamente todo o site privado.


57. SEGURANÇA E CONTEÚDO GERADO
-------------------------------

Um modelo de linguagem pode produzir:

- informação incorreta;
- código inseguro;
- instruções incompletas;
- conteúdo enviesado;
- respostas que parecem confiantes sem estarem corretas.

Para casos reais, é necessário:

- informar que o conteúdo é gerado por IA;
- validar resultados críticos;
- não executar código gerado automaticamente;
- limitar tamanhos de entrada;
- aplicar políticas adequadas ao domínio;
- registrar erros técnicos sem guardar dados sensíveis;
- criar fallback quando o modelo falhar.

Em áreas médicas, jurídicas ou financeiras, uma resposta fluente não substitui
validação profissional.


58. O MODELO PODE ALUCINAR
--------------------------

Alucinação é quando o modelo gera informação falsa ou não sustentada, mas com
aparência convincente.

Isso acontece porque o objetivo básico da geração é produzir uma sequência
plausível, não consultar automaticamente uma fonte verdadeira.

Formas de reduzir o risco:

- dar contexto confiável;
- solicitar que admita incerteza;
- limitar a tarefa;
- usar recuperação de documentos;
- exigir referências verificáveis;
- validar respostas;
- não usar o modelo como única fonte de verdade.

Temperature baixa pode tornar a saída mais previsível, mas não elimina
alucinações.

73. RECUPERAÇÃO DE CONHECIMENTO
-------------------------------

O modelo local responde com conhecimento aprendido e contexto do prompt.

Para responder usando documentos privados ou atualizados, poderíamos adicionar:

1. armazenamento dos documentos;
2. divisão em trechos;
3. busca pelos trechos relevantes;
4. montagem de contexto;
5. envio do contexto ao modelo;
6. resposta com referência à fonte.

Esse padrão é conhecido como RAG:

    Retrieval-Augmented Generation

O conceito se conecta à Aula 2:

- embeddings representam conteúdo;
- busca vetorial encontra proximidade semântica;
- o modelo usa os resultados como contexto.

80. GLOSSÁRIO
-------------

AbortController
    controlador usado para cancelar operações assíncronas.

AbortSignal
    sinal entregue à operação para comunicar cancelamento.

API
    contrato usado por programas para acessar funcionalidades.

Async generator
    função que produz valores assíncronos ao longo do tempo.

Availability
    estado de disponibilidade do modelo.

Built-in AI
    recursos de inteligência artificial integrados à plataforma.

Chunk
    parte de um dado transmitido em streaming.

CORS
    regras para compartilhamento de recursos entre origens.

DOM
    representação dos elementos HTML acessível pelo JavaScript.

Feature detection
    verificação da existência real de um recurso antes do uso.

Gemini Nano
    modelo compacto da família Gemini para execução local compatível.

Gesto do usuário
    ativação explícita como clique, toque ou tecla.

IIFE
    função criada e executada imediatamente.

Inferência
    uso de um modelo já treinado para gerar uma previsão ou resposta.

LanguageModel
    interface da Prompt API usada para disponibilidade e sessões.

LLM
    Large Language Model, modelo de linguagem de grande porte.

Modelo local
    modelo executado no dispositivo do usuário.

Origin
    combinação de protocolo, host e porta que identifica a origem.

Prompt
    instrução e contexto enviados ao modelo.

Prompt API
    API do Chrome usada para conversar com o modelo integrado.

Sessão
    contexto de interação criado para usar o modelo.

Streaming
    entrega progressiva de dados.

System prompt
    mensagem que orienta papel e comportamento do modelo.

Temperature
    parâmetro que influencia aleatoriedade na amostragem.

Token
    unidade de texto processada pelo modelo.

topK
    limite de candidatos considerados na seleção do próximo token.

User prompt
    solicitação feita pela pessoa.

yield
    instrução que entrega um valor e pausa uma função geradora.

91. DÚVIDA IMPORTANTE: CHROME, GEMINI API E OLLAMA
--------------------------------------------------

DÚVIDA QUE SURGIU DURANTE A AULA

Se o Gemini Nano está baixado no computador e usa a CPU ou GPU local, por que
isso seria diferente de criar um projeto comum, baixar uma IA e executá-la
localmente?

RESPOSTA

O conceito principal é realmente o mesmo:

    modelo instalado no computador
            |
            v
    CPU ou GPU do cliente
            |
            v
    resposta gerada localmente

A diferença não está no resultado visual.

A diferença está em quem administra as partes necessárias para o modelo
funcionar.

Um modelo local precisa de pelo menos três camadas:

1. pesos do modelo;
2. motor de inferência;
3. API para a aplicação conversar com esse motor.

NA PROMPT API DO CHROME

O Chrome administra:

- download do Gemini Nano;
- escolha da variante adequada ao hardware;
- armazenamento;
- atualizações;
- remoção quando necessário;
- motor de inferência;
- uso de CPU ou GPU;
- isolamento e permissões;
- API LanguageModel.

Nosso projeto apenas utiliza a interface fornecida:

    projeto
        |
        v
    LanguageModel
        |
        v
    Gemini Nano administrado pelo Chrome

Por isso, podemos dizer de maneira informal que o Google e o Chrome entregam a
infraestrutura "mastigada".

O Gemini Nano realmente fica armazenado e é executado no computador, mas seus
arquivos e seu motor são internos ao Chrome. A forma suportada de acessá-lo é
pela API LanguageModel.

NA GEMINI API DA NUVEM

O fluxo é diferente:

    projeto
        |
        v
    backend com chave protegida
        |
        v
    internet
        |
        v
    servidores do Google
        |
        v
    resposta

Nesse caso, o Google administra o modelo e também realiza o processamento em
seus próprios servidores.

O cliente não precisa baixar o modelo e não usa sua GPU para a inferência.

A aplicação envia a solicitação e recebe a resposta, mas precisa cuidar de:

- backend seguro;
- proteção da chave;
- autenticação;
- limites de requisição;
- custos;
- erros de rede;
- privacidade dos dados;
- disponibilidade do serviço.

COM OLLAMA LOCAL

O fluxo seria:

    projeto
        |
        v
    API local do Ollama
        |
        v
    motor do Ollama
        |
        v
    modelo local
        |
        v
    CPU ou GPU do cliente

Ollama também entrega muita complexidade pronta.

ESCLARECIMENTO DA DÚVIDA

A dúvida não é sobre programar ou treinar uma rede neural do zero.

Ela é sobre ter de programar, configurar e administrar toda a camada necessária
para transformar o modelo local em uma funcionalidade segura do projeto.

Nesse sentido, o entendimento está correto.

O desenvolvedor ou o usuário teria de cuidar de mais partes:

- instalar o Ollama;
- escolher um modelo compatível;
- executar o download do modelo;
- escolher a versão e a quantização do modelo;
- garantir espaço em disco;
- verificar memória e hardware;
- iniciar e manter o serviço local;
- configurar o endereço da API;
- permitir a comunicação entre aplicação e serviço local;
- distribuir instruções de instalação;
- atualizar o modelo;
- tratar máquinas sem Ollama;
- cuidar da segurança da porta local;
- decidir quais origens podem acessar o serviço;
- configurar limites de requisição e concorrência;
- limitar o tamanho dos prompts e das respostas;
- configurar temperature, topK e outros parâmetros;
- gerenciar contexto e histórico da conversa;
- construir system prompts e regras da aplicação;
- cancelar gerações;
- tratar erros e indisponibilidade;
- validar e exibir a saída com segurança;
- monitorar consumo de memória, CPU e GPU.

O Ollama carrega e executa os pesos, mas o projeto ainda precisa escolher qual
arquivo ou variante do modelo será utilizado.

É importante distinguir:

pesos do modelo:
    números aprendidos durante o treinamento;
    normalmente não são editados individualmente pela aplicação;

versão ou arquivo de pesos:
    modelo e quantização que serão baixados e executados;
    isso precisa ser escolhido e administrado;

parâmetros de inferência:
    temperature, topK, tamanho do contexto e outras opções;
    isso precisa ser configurado ou enviado pela aplicação.

Portanto:

- a API do Chrome administra o Gemini Nano local para nós;
- o Chrome também define valores padrão e limita quais parâmetros a página pode
  controlar;
- a Gemini API administra um modelo remoto para nós;
- o Ollama administra boa parte da inferência local, mas nós administramos sua
  instalação, seus modelos, seus parâmetros e sua integração;
- mesmo com Chrome ou Gemini API, o projeto ainda é responsável pela segurança
  da própria interface, pelas regras de negócio e pelo uso responsável da saída.

COMPARAÇÃO FINAL

Prompt API + Gemini Nano:
    processamento local;
    Chrome administra o modelo e o motor.

Gemini API:
    processamento remoto;
    Google administra o modelo, o motor e os servidores.

Ollama:
    processamento local;
    Ollama administra o motor;
    projeto e usuário administram a instalação e o modelo.

CONCLUSÃO DA DÚVIDA

É possível construir uma experiência visualmente igual usando qualquer uma
dessas arquiteturas.

O que muda é:

- onde a resposta é processada;
- quem baixa o modelo;
- quem fornece o motor;
- quem administra atualizações;
- quem paga os recursos computacionais;
- quais dados saem do dispositivo;
- quanto trabalho de instalação e manutenção fica com o desenvolvedor.

FRASE PARA LEMBRAR

"Na Aula 4, não aprendemos apenas a executar uma IA local: aprendemos a utilizar
