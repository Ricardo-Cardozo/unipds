AULA EXTRA — GRAFANA, OBSERVABILIDADE E OPENTELEMETRY
====================================================

Projeto Alumnus / N|Sentinel para visualizar a saúde do sistema e investigar
problemas com métricas, logs, traces, alertas e Inteligência Artificial.

Data da análise do projeto: 30/08/2026


OBJETIVO DA AULA
----------------

Esta aula apresenta uma stack completa de observabilidade executada com Docker.

O projeto permite:

- acompanhar se os serviços estão disponíveis;
- medir quantidade, duração e erros das requisições;
- centralizar logs;
- visualizar o caminho de uma requisição;
- correlacionar métricas, logs e traces;
- criar e avaliar alertas;
- investigar um bug realista de vazamento de conexões PostgreSQL;
- consultar a stack por Grafana MCP;
- entender o papel do OpenTelemetry.

Resposta curta para a dúvida inicial:

    Sim, este projeto usa OpenTelemetry.

A aplicação Node.js produz traces, métricas e logs. Ela envia esses sinais por
OTLP/gRPC para o OpenTelemetry Collector. O Collector distribui os sinais para
Tempo, Loki e Prometheus. O Grafana consulta esses backends e apresenta uma visão
unificada da saúde e do comportamento do sistema.


1. O QUE ESTE PROJETO REALMENTE É
----------------------------------

O projeto não é apenas um dashboard bonito.

Ele é um laboratório de observabilidade composto por:

- uma aplicação Fastify em TypeScript;
- um banco PostgreSQL;
- instrumentação OpenTelemetry;
- OpenTelemetry Collector;
- Prometheus;
- Loki;
- Tempo;
- Grafana;
- Blackbox Exporter;
- regras de alerta;
- dashboards provisionados;
- testes de telemetria;
- Grafana MCP;
- um cenário proposital de falha.

Seu objetivo didático é mostrar como detectar e explicar problemas que seriam
difíceis de entender apenas olhando uma mensagem de erro.


2. MONITORAMENTO E OBSERVABILIDADE
---------------------------------

Monitoramento costuma responder perguntas conhecidas:

- o serviço está online?
- a latência passou do limite?
- a taxa de erro está alta?
- o banco aceita conexão?

Observabilidade ajuda a investigar perguntas que ainda não estavam previstas:

- por que as duas primeiras requisições funcionam e as seguintes falham?
- qual operação ficou lenta?
- qual consulta de banco pertence a esta requisição?
- qual erro apareceu no mesmo trace?
- a falha é na aplicação ou na infraestrutura?

Monitoramento detecta sintomas. Observabilidade fornece evidências para explorar
o estado interno do sistema.


3. TELEMETRIA
-------------

Telemetria é o conjunto de sinais enviados pelo sistema para que possamos
entender seu comportamento.

Os sinais principais desta aula são:

1. métricas;
2. logs;
3. traces.

OpenTelemetry também trabalha com contexto distribuído e baggage. Perfis são
outro sinal relacionado à observabilidade moderna, mas não fazem parte desta
stack atual.


4. MÉTRICAS
-----------

Métricas são valores numéricos observados ao longo do tempo.

Exemplos:

- quantidade de requisições;
- taxa de respostas 500;
- duração média;
- p95 de latência;
- conexões em uso;
- probe_success;
- memória utilizada;
- quantidade de spans exportados.

São excelentes para:

- dashboards;
- tendências;
- agregações;
- alertas;
- comparar antes e depois;
- responder "quanto?" e "com que frequência?".


5. LOGS
-------

Logs são registros de eventos.

Exemplos do projeto:

    Processing student query request
    Error processing request
    Manual reset requested
    DB Leaky Connections scenario initialized

Logs podem conter:

- data e hora;
- nível;
- mensagem;
- stack trace;
- service.name;
- trace_id;
- span_id;
- atributos estruturados.

Eles ajudam a responder:

- o que a aplicação registrou?
- qual erro foi lançado?
- qual arquivo aparece no stack trace?
- em que ordem os eventos ocorreram?


6. TRACES
---------

Um trace representa o caminho de uma operação pelo sistema.

Cada etapa é normalmente representada por um span.

Exemplo:

    trace da requisição GET
        |
        +-- span Fastify
        |
        +-- span para adquirir conexão PostgreSQL
        |
        +-- span SELECT
        |
        +-- status e duração

Um trace ajuda a responder:

- onde o tempo foi gasto?
- qual componente falhou?
- qual foi a hierarquia das operações?
- quais atributos pertencem à requisição?
- qual log foi produzido durante esse caminho?


7. CORRELAÇÃO DOS SINAIS
--------------------------

Separadamente:

- métrica mostra que erros aumentaram;
- log mostra timeout ao obter conexão;
- trace mostra a operação e sua duração.

Juntos:

    sintoma -> evento detalhado -> caminho da requisição -> causa provável

Uma investigação forte cruza os sinais em vez de confiar em apenas um gráfico.

14. INSTRUMENTAÇÃO AUTOMÁTICA
-------------------------------

getNodeAutoInstrumentations ativa instrumentações suportadas para bibliotecas

O projeto desabilita Fastify e Knex dentro do pacote genérico e adiciona essas
duas explicitamente:

    FastifyOtelInstrumentation
    KnexInstrumentation

Motivo registrado no código:

Sem esse cuidado, uma mesma operação poderia gerar spans duplicados ou confusos.


15. EXPORTAÇÃO DE MÉTRICAS
----------------------------

O PeriodicExportingMetricReader está configurado com:

    exportIntervalMillis: 3000

Isso significa que o SDK tenta exportar métricas a cada três segundos.

O destino padrão vem de:

    OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317

No ambiente Docker interno, o endpoint correspondente deve apontar para:

    http://opentelemetry-collector:4317


16. PROCESSAMENTO DE SPANS
-------------------------

O BatchSpanProcessor acumula spans e exporta em lotes.

Configuração do projeto:

- fila máxima: 2048;
- lote máximo: 512;
- atraso programado: 5000 ms;
- timeout de exportação: 30000 ms.

O lote reduz a sobrecarga de enviar cada span individualmente.

No encerramento, shutDownOtel chama sdk.shutdown() para tentar descarregar a
telemetria restante.


17. O QUE É OTLP
-----------------

OTLP significa OpenTelemetry Protocol.

É o protocolo usado para transportar sinais OpenTelemetry.

Neste projeto, a aplicação envia por OTLP/gRPC na porta 4317.

OTLP não é:

- Grafana;
- Prometheus;
- um banco;
- um dashboard.

Ele é o formato e protocolo de transporte entre componentes de telemetria.


18. OPENTELEMETRY COLLECTOR
---------------------------

O Collector funciona como hub central e independente de fornecedor.

Responsabilidades:

- receber telemetria;
- processar;
- agrupar;
- tentar novamente em falhas configuradas;
- exportar para backends diferentes;
- expor sua própria saúde e métricas.

Vantagem arquitetural:

    a aplicação conhece OTLP e o Collector;
    ela não precisa conhecer detalhes de Tempo, Loki e Prometheus.


19. RECEIVER, PROCESSOR E EXPORTER
---------------------------------

RECEIVER

Recebe dados.

No projeto:

    receiver OTLP/gRPC em 0.0.0.0:4317

PROCESSOR

Transforma, agrupa, filtra ou enriquece.

No projeto:

    batch

EXPORTER

Envia o resultado ao destino.

No projeto:

- otlp/tempo;
- otlphttp/loki;
- prometheus.


20. PIPELINES DO COLLECTOR
--------------------------

Pipeline de traces:

    receiver otlp -> processor batch -> exporter otlp/tempo

Pipeline de métricas:

    receiver otlp -> processor batch -> exporter prometheus

Pipeline de logs:

    receiver otlp -> processor batch -> exporter otlphttp/loki

O mesmo receiver recebe os três tipos, mas cada pipeline possui seu tipo e seu
destino.

22. PROMETHEUS
--------------

Prometheus é o backend de métricas e mecanismo de alertas por regras.

Ele armazena séries temporais formadas por:

- nome da métrica;
- labels;
- valor;
- timestamp.

Exemplo:

    probe_success{job="blackbox-http",instance="http://grafana:3000/api/health"} 1

Neste projeto, Prometheus:

- faz scrape do exporter do Collector em :8889;
- coleta métricas internas de Tempo;
- coleta métricas internas de Grafana;
- coleta métricas internas de Loki;
- coleta métricas do Blackbox Exporter;
- executa probes HTTP, TCP e ICMP via Blackbox;
- avalia alerts.yaml;
- aceita remote write do gerador de métricas do Tempo;
- guarda exemplars.


23. MODELO PULL DO PROMETHEUS
----------------------------

O Prometheus normalmente busca métricas nos alvos por HTTP.

No fluxo da aplicação existem duas etapas:

1. a aplicação empurra métricas por OTLP para o Collector;
2. o Collector expõe essas métricas em :8889 e o Prometheus faz scrape.

Portanto:

    app faz push para Collector;
    Prometheus faz pull do Collector.


24. PROMQL
----------

PromQL é a linguagem de consulta do Prometheus.

Consultas presentes ou relacionadas ao projeto:

Ver saúde dos alvos de scrape:

    up

Ver probes:

    probe_success

Ver probes HTTP:

    probe_success{job="blackbox-http"}

Ver duração da probe:

    probe_duration_seconds{job="blackbox-http"}

Teste automatizado da aplicação:

    http_client_request_duration_seconds_count{exported_job="NOME_DO_SERVICO"}

Os dashboards também usam nomes normalizados como:

    http_server_duration_milliseconds_count
    http_server_duration_milliseconds_sum

Os nomes podem variar com versão das convenções e normalização do Collector.
Antes de copiar uma query, confirme o nome real no explorador de métricas do
Prometheus.


25. LABELS E CARDINALIDADE
-------------------------

Labels tornam métricas multidimensionais.

Boas labels:

- service_name;
- http_method;
- http_route;
- http_status_code;
- environment.

Labels perigosas:

- user_id;
- request_id;
- UUID aleatório;
- URL completa com parâmetros;
- mensagem de erro inteira.

Valores quase únicos geram alta cardinalidade, aumentam custo de memória e
armazenamento e podem degradar consultas.


26. LOKI
--------

Loki é o backend de agregação de logs.

Neste projeto:

- recebe logs do Collector via OTLP/HTTP;
- escuta API HTTP na porta 3100;
- usa armazenamento local;
- usa schema v13;
- trabalha sem autenticação no laboratório;
- é configurado como datasource do Grafana.

Loki indexa principalmente labels dos streams em vez de indexar integralmente o
conteúdo de cada linha.


27. LOGQL
---------

LogQL é a linguagem de consulta do Loki.

Consulta usada pelos testes:

    {service_name="NOME_DO_SERVICO"}

Exemplo para procurar erros:

    {service_name="NOME_DO_SERVICO"} |= "Error"

Exemplo conceitual para JSON estruturado:

    {service_name="NOME_DO_SERVICO"} | json | level="error"

Sempre limite a janela temporal. Consultas amplas em logs podem processar grande
volume e revelar informações sensíveis.


28. TEMPO

Tempo é o backend de tracing distribuído.

No projeto:

- retém traces por 24 horas para a demonstração;
- gera service graphs;
- gera span metrics;
- envia métricas derivadas ao Prometheus;
- envia exemplars;

37. BLACKBOX EXPORTER
---------------------

Blackbox Exporter observa um serviço de fora.

Ele não pergunta apenas ao processo sobre suas métricas internas. Ele tenta
realizar uma operação real:

- requisição HTTP;
- conexão TCP;
- ICMP ping.

Métrica central:

    probe_success

Valor 1:

    probe funcionou.

Valor 0:

    probe falhou.

39. O QUE A BLACKBOX PROBE NÃO GARANTE
--------------------------------------

HTTP 200 não prova que toda regra de negócio funciona.

TCP aberto não prova que uma consulta de banco terá sucesso.

ICMP respondendo não prova que a API está saudável.

Combine:

- health check;
- métricas da aplicação;
- logs;
- traces;
- teste sintético do comportamento mais importante.

42. CENÁRIO DB LEAKY CONNECTIONS
--------------------------------

Arquivo:

Objetivo:

Configuração:

- timeout para conexão de um segundo;
- cada requisição chama pool.connect();
- a conexão obtida não é liberada.


43. O BUG PROPOSITAL
--------------------

Trecho conceitual:

    const client = await pool.connect()
    const result = await client.query(...)
    return result

O que falta:

    client.release()

Consequência:

1. primeira requisição pega conexão A;
2. segunda requisição pega conexão B;
3. nenhuma é devolvida;
4. terceira requisição espera;
5. apó um segundo, o pool gera timeout;
6. a API retorna HTTP 500;
7. as seguintes continuam falhando.


44. ENDPOINTS DO CENÁRIO
-------------------------

Gerar a falha:

    GET /students/db-leaky-connections

Resetar conexões vazadas:

    POST /students/db-leaky-connections/reset

Exemplos:

    curl http://localhost:9000/students/db-leaky-connections

    curl -X POST http://localhost:9000/students/db-leaky-connections/reset

O reset é didático. A correção real é liberar cada conexão no fluxo normal.


45. CORREÇÃO DO BUG
----------------------

Padrão correto:

    const client = await pool.connect()

    try {
      const result = await client.query(
        'SELECT * FROM students LIMIT 1'
      )

      return result.rows
    } finally {
      client.release()
    }

O finally executa tanto no sucesso quanto no erro.

Outra opção é usar uma API de pool que execute a consulta sem manter manualmente
um client quando não há necessidade de transação dedicada.


46. INVESTIGAÇÃO PASSO A PASSO
--------------------------------

1. Métrica

Identificar aumento de respostas 500 e duração próxima de um segundo.

2. Padrão

Observar duas respostas boas seguidas por falhas.

3. Logs

Buscar "Error processing request" e a mensagem de timeout do pg-pool.

4. Trace

Abrir trace da requisição com erro.

5. Spans de banco

Ver onde a espera ocorreu.

6. Código

Conferir pool.connect e ausência de release.

7. Hipótese

O pool de tamanho dois está esgotado.

8. Teste

Resetar e repetir: duas funcionam, terceira falha.

9. Correção

Adicionar finally com client.release().

10. Verificação

Executar várias chamadas e confirmar ausência de timeout e queda dos erros.


47. POR QUE UMA MÉTRICA SOZINHA NÃO BASTA
------------------------------------------

A taxa de 500 mostra o sintoma.

Ela não prova sozinha:

- vazamento de conexão;
- local exato do código;
- falta de release;
- tamanho do pool;
- stack trace.

Para causa raiz, combine métrica, log, trace, reprodução e inspeção do código.

Telemetria é assíncrona.

Entre uma requisição e a informação ficar consultável existem:

- exportação do Collector;
- scrape do Prometheus;
- indexação do Tempo;
- ingestão do Loki.

Por isso os testes aguardam e tentam consultar novamente.

Retry deve ter:

- limite;
- atraso;
- erro final claro.


50. ALERTAS DO PROMETHEUS
------------------------

O arquivo prometheus/alerts.yaml define, entre outros:

- ServiceDown;
- DatabaseDown;
- ServiceUnreachable;
- ServiceSlowResponse;
- SSLCertificateExpiringSoon;
- ServiceHealthCheckFailed;
- HighMemoryUsage;
- PrometheusCompactionFailing;
- NoMetricsScraped;
- HighScrapeDuration;
- PostgreSQLDown.

Uma regra possui:

- expr;
- duração for;
- labels;
- annotations.


51. ESTADOS DE UMA REGRA DE ALERTA
---------------------------------

Normal:

    condição não foi atendida.

Pending:

    condição foi atendida, mas ainda não completou o tempo de for.

Firing:

    condição permaneceu verdadeira durante o período exigido.

O campo for reduz alertas por falhas muito curtas.


52. ALERTMANAGER NÃO ESTÁ ATIVO NESTE SNAPSHOT
-----------------------------------------------

prometheus.yaml possui uma lista vazia de destinos de Alertmanager.

Isso significa:

- Prometheus avalia as regras;
- é possível consultar alertas;
- não existe, nessa configuração, um Alertmanager recebendo e roteando essas
  notificações para e-mail, Slack ou outro canal.

Para produção, falta configurar roteamento, agrupamento, silêncio e canais.


53. ALERTING DO GRAFANA
-----------------------

O projeto também provisiona regras no próprio Grafana.

Exemplos:

- HTTP Service Down;
- Database Connection Failed;
- Service Network Unreachable;
- Service Slow Response.

Grafana Alerting pode consultar diferentes datasources e centralizar regras.

Cuidados:

- não duplicar a mesma notificação em Prometheus e Grafana;
- definir responsável por cada regra;
- testar NoData e Error;
- evitar fadiga de alertas;
- definir canal e escalonamento.


54. RED E GOLDEN SIGNALS
------------------------

RED para serviços:

- Rate: taxa de requisições;
- Errors: taxa de erros;
- Duration: duração.

Golden Signals:

- latência;
- tráfego;
- erros;
- saturação.

O cenário de conexões apresenta:

- tráfego gerado a cada dois segundos;
- erros 500;
- duração de falha próxima ao timeout;
- saturação do pool.


55. SLI, SLO E SLA
------------------

SLI:

    indicador medido.

Exemplo:

    proporção de requisições bem-sucedidas.

SLO:

    objetivo interno para o indicador.

Exemplo:

    99,9% das requisições devem funcionar em 30 dias.

SLA:

    compromisso formal com consequências acordadas.

Grafana e Prometheus ajudam a medir SLIs e observar SLOs, mas a definição do
objetivo depende do produto e do negócio.

74. SEGURANÇA: GRAFANA MCP SEM TOKEN

O contêiner mcp-grafana recebe GRAFANA_URL, mas não recebe service account token.

Para ambiente real:

- desabilite acesso anônimo;
- crie service account específica;
- use token de menor privilégio;
- comece com --disable-write;
- restrinja consultas;
- use autenticação no endpoint MCP;
- use TLS;
- registre auditoria sem segredos.

86. RESPOSTAS RÁPIDAS
---------------------

OpenTelemetry:

    gera, coleta e padroniza telemetria; não é o dashboard.

Collector:

    recebe, processa e distribui sinais.

Prometheus:

    armazena e consulta métricas, além de avaliar regras.

Loki:

    armazena e consulta logs.

Tempo:

    armazena e consulta traces.

Grafana:

    visualiza, explora, correlaciona e alerta.

Blackbox:

    testa a saúde a partir de fora do serviço.

Grafana MCP:

    oferece ferramentas de observabilidade a um agente de IA.


87. RESUMO DIDÁTICO
--------------------

A aplicação é instrumentada pelo OpenTelemetry e envia métricas, logs e traces
ao Collector. O Collector encaminha traces para Tempo, logs para Loki e expõe
métricas para Prometheus. Grafana consulta os três backends e correlaciona os
sinais. Blackbox Exporter testa se componentes respondem. Alertas detectam
condições ruins. O Grafana MCP permite investigar esses dados com um agente.

O cenário didático vaza duas conexões de banco e faz as chamadas seguintes
falharem. A stack mostra o sintoma nas métricas, a mensagem nos logs e o caminho
nos traces, permitindo chegar à falta de client.release().


88. RESUMO EXTREMAMENTE CURTO
----------------------------

OpenTelemetry coleta os sinais; Prometheus guarda métricas, Loki guarda logs,
Tempo guarda traces e Grafana mostra tudo para entender a saúde do sistema.
