1. QUAL É O PROBLEMA DA AULA 3?
-------------------------------

O Duck Hunt é um jogo em que alvos se movimentam pela tela e o jogador precisa
clicar na posição correta para acertá-los.

O desafio é fazer uma IA jogar automaticamente.

O sistema precisa responder repetidamente:

1. O que está visível?
2. Existe um objeto reconhecível?
3. Qual é sua classe?
4. Qual é a confiança?
5. Onde está sua caixa?
6. Qual é o centro da caixa?
7. Como transformar o centro em clique?

Não basta saber que existe um objeto. Precisamos de sua localização.


2. CLASSIFICAÇÃO E DETECÇÃO
---------------------------

CLASSIFICAÇÃO

Entrada:
    uma imagem;

Saída:
    uma classe.

Exemplo:

imagem -> pássaro

Ela não informa onde o pássaro está.

DETECÇÃO

Entrada:
    uma imagem;

Saída:
    classe + confiança + bounding box.

Exemplo:

imagem -> kite, 87%, [x1, y1, x2, y2]

Para mover a mira precisamos de detecção.


3. VISÃO COMPUTACIONAL
----------------------

Visão computacional permite extrair informações de imagens e vídeos.

Algumas tarefas:

- classificação;
- detecção;
- segmentação;
- leitura de texto;
- estimativa de pose;
- reconhecimento;
- rastreamento.

Nesta aula, a tela do jogo é tratada como uma sequência de imagens.


4. O QUE É YOLO?
----------------

YOLO significa:

You Only Look Once

É uma família de detectores que analisa a imagem de forma integrada.

Usamos YOLOv5n:

YOLO:
    família;

v5:
    versão;

n:
    variante nano.

A variante nano prioriza velocidade e tamanho menor, características úteis para
uma demonstração executada no navegador.


5. MODELO PRÉ-TREINADO
----------------------

Na Aula 2, criamos e treinamos uma rede neural.

Na Aula 3:

- não treinamos o YOLO no navegador;
- carregamos pesos já treinados;

- processamos a saída;
- integramos a previsão ao jogo.

Treinamento:

dados + algoritmo -> pesos aprendidos

Inferência:

imagem + pesos aprendidos -> previsão


6. GRAPHMODEL E ARQUIVOS
------------------------

O modelo usa o formato GraphModel do TensorFlow.js.

Arquivos:

model.json
    grafo, operações e metadados;

group1-shard1of2.bin
    primeiro bloco de pesos, aproximadamente 4 MB;

group1-shard2of2.bin
    segundo bloco, aproximadamente 3,2 MB;

labels.json
    nomes das 80 classes.

Carregamento:

tf.loadGraphModel(MODEL_PATH)

GraphModel é diferente de um modelo Sequential criado diretamente no browser.


7. AS 80 CLASSES E A CLASSE KITE
--------------------------------

O labels.json contém classes do conjunto COCO, como:

- person;
- car;
- airplane;
- bird;
- dog;
- kite;
- sports ball;
- bottle;
- chair;
- laptop;
- cell phone;
- book;
- teddy bear.

O código final filtra:

kite

O modelo retorna índice numérico. O labels.json converte:

índice 0 -> person
índice 14 -> bird
índice 33 -> kite

O jogo mostra patos, mas o modelo não foi treinado especificamente com esses
sprites. Usar kite é uma decisão prática da demonstração.

Uma solução especializada deveria treinar ou ajustar um detector para os sprites
reais e usar uma classe própria, como duck ou target.

11. INICIALIZAÇÃO DO JOGO
-------------------------

O main.js da raiz espera DOMContentLoaded.

Depois:

1. cria Game;
2. informa sprites.json;
3. espera game.load();
4. inicia machine-learning/main.js.

Fluxo:

DOM pronto
    -> new Game()
    -> game.load()
    -> PixiJS e texturas
    -> Stage
    -> jogo
    -> integração com IA

O await evita acessar game.stage antes da inicialização.


12. GAME.LOAD()
---------------

Game.load() cria PIXI.Application.

Configura:

- largura da janela;
- altura da janela;
- fundo azul;
- canvas no body.

Depois carrega o spritesheet e chama onLoad().

onLoad():

- cria Stage;
- adiciona Stage;
- escala para a janela;
- cria links do HUD;
- registra eventos;
- inicia fase;
- inicia animação.


13. STAGE E COORDENADAS
-----------------------

Stage estende PIXI.Container.

Ele agrupa:

- fundo;
- árvore;
- cachorro;
- patos;
- clarão;
- HUD;
- mira.

Sistema lógico:

MAX_X = 800
MAX_Y = 600

Escala:

scale.x = largura da janela / 800
scale.y = altura da janela / 600

Existem coordenadas globais da tela e coordenadas lógicas do jogo.


14. A MIRA
----------

Aim estende PIXI.Sprite.

Configuração:

- textura aim/0.png;
- tamanho 40 x 40;
- posição inicial 350, 350;
- limites do Stage.

Métodos:

setPosition(x, y)
    posição absoluta;

move(x, y)
    deslocamento relativo;

reset()
    volta ao início e oculta.

A IA usa setPosition(), porque a previsão representa posição absoluta.


15. HANDLECLICK E DISPARO
-------------------------

Game.handleClick(event) recebe:

event.global.x
event.global.y

Primeiro verifica links de pause, mute, fullscreen, criação de fase e replay.

Se o jogo está ativo:

1. toca o tiro;
2. reduz uma bala;
3. chama stage.shotsFired();
4. atualiza a pontuação.

A IA reutiliza esse mesmo fluxo, simulando um evento compatível.


16. COMO O ACERTO É CONFIRMADO
------------------------------

Stage.shotsFired():

1. mostra clarão;
2. percorre os patos;
3. confirma se estão vivos;
4. converte clique global para escala lógica;
5. mede distância;
6. compara com o raio;
7. chama duck.shot();
8. devolve a quantidade atingida.

Conversão:

x lógico = x global / scale.x
y lógico = y global / scale.y


17. HUD DA IA
-------------

layout.js cria:

- scoreText;
- predictionsText.

Exibição:

Score: confiança
Predictions: (x, y)

O HUD usa fonte monospace e fica no canto superior direito.

Ao redimensionar:

1. mede os textos;
2. consulta renderer.width;
3. recalcula hud.x;
4. mantém margem de 16 pixels.

O Score desse HUD é confiança da detecção, não a pontuação total do jogo.


18. POR QUE WEB WORKER?
-----------------------

A thread principal cuida de:

- eventos;
- renderização;
- animação;
- interface.

Inferência é pesada e pode travar o jogo.

Divisão:

THREAD PRINCIPAL

- renderiza;
- captura canvas;
- recebe previsão;
- move mira;
- dispara.

WORKER

- carrega TensorFlow.js;
- carrega modelo;
- cria tensores;
- infere;
- processa detecções.


19. WORKER CLÁSSICO
-------------------

worker.js usa:

importScripts(URL_DO_TENSORFLOW)

importScripts() pertence ao Worker clássico.

Por isso usamos:

new Worker(new URL('./worker.js', import.meta.url))

Não usamos type: module.

Misturar Worker módulo com importScripts() causaria erro em execução.


20. PROTOCOLO DE MENSAGENS
--------------------------

Principal para Worker:

{
    type: predict,
    image: bitmap
}

Worker para principal:

{
    type: prediction,
    x,
    y,
    score
}

O Worker também informa:

{
    type: model-loaded
}

O campo type cria um protocolo extensível e evita tratar todas as mensagens da
mesma forma.


21. CAPTURA DO CANVAS
---------------------

O código extrai a cena:

canvas = game.app.renderer.extract.canvas(game.stage)

Depois:

bitmap = await createImageBitmap(canvas)

Fluxo:

objetos PixiJS
    -> canvas
    -> ImageBitmap
    -> Worker
    -> tensor

O modelo não conhece Game, Duck ou Stage. Ele recebe pixels.


22. INTERVALO DE 200 MS
-----------------------

setInterval executa uma tentativa a cada 200 milissegundos.

Em condição ideal:

1000 / 200 = 5 tentativas por segundo

Isso não garante cinco inferências concluídas por segundo.

Se a inferência demorar mais de 200 ms:

- solicitações podem acumular;
- a previsão pode ficar atrasada;
- CPU/GPU podem permanecer saturadas;
- a mira pode perseguir posição antiga.

Melhoria:

Enviar nova imagem somente quando o Worker responder ou informar que está livre.
Isso é controle de backpressure.


23. TRANSFER LIST
-----------------

O envio usa:

worker.postMessage(mensagem, [bitmap])

O segundo argumento transfere o ImageBitmap.

Vantagens:

- evita cópia grande;
- reduz custo de memória;
- melhora comunicação.

Depois da transferência, a thread principal não deve reutilizar o bitmap.


24. CARREGAMENTO DO TENSORFLOW.JS
---------------------------------

No Worker:

importScripts('https://cdn.jsdelivr.net/npm/@tensorflow/tfjs@latest')

Depois:

await tf.ready()

Ordem:

1. carregar biblioteca;
2. esperar backend;
3. carregar labels;
4. carregar modelo;
5. aquecer;
6. aceitar imagens.

Limitação:

latest não fixa versão. Uma atualização do CDN pode mudar compatibilidade.

Para reprodutibilidade, fixar uma versão conhecida.


25. CAMINHOS E COPYWEBPACKPLUGIN
--------------------------------

Constantes:

MODEL_PATH = yolov5n_web_model/model.json
LABELS_PATH = yolov5n_web_model/labels.json

CopyWebpackPlugin copia:

machine-learning/yolov5n_web_model

para:

dist/yolov5n_web_model

Sem isso, model.json e os pesos retornariam 404.


26. LABELS
----------

O Worker faz fetch de labels.json e converte para array.

O modelo retorna classes numéricas por eficiência.

Exemplo:

classIndex = 33
labels[33] = kite

Sem os labels, teríamos apenas números.


27. CARREGAMENTO DO GRAPHMODEL
------------------------------

model = await tf.loadGraphModel(MODEL_PATH)

O navegador:

1. busca model.json;
2. lê o grafo;
3. encontra os shards;
4. baixa os pesos;
5. monta o modelo.

Se model ainda não existe, predict retorna imediatamente.

Essa guarda evita executeAsync() sobre valor nulo.


28. WARMUP
----------

O aquecimento cria:

dummyInput = tf.ones(model.inputs[0].shape)

Depois executa:

await model.executeAsync(dummyInput)

Motivos:

- preparar kernels;
- alocar recursos;
- inicializar operações;
- reduzir custo da primeira imagem real.

O dummyInput é descartado.

Ponto de melhoria:

As saídas da inferência de warmup também devem ser explicitamente descartadas,
pois executeAsync() produz tensores.


29. FORMATO DE ENTRADA
----------------------

Formato final:

[1, 640, 640, 3]

1:
    batch;

640:
    altura;

640:
    largura;

3:
    canais RGB.

expandDims(0) adiciona o batch.


30. PRÉ-PROCESSAMENTO
---------------------

preprocessImage():

1. tf.browser.fromPixels(input);
2. tf.image.resizeBilinear(image, [640, 640]);
3. div(255);
4. expandDims(0).

fromPixels:
    imagem para tensor;

resize:
    tamanho esperado;

div:
    normalização;

expandDims:
    batch.


31. FROMPIXELS
--------------

fromPixels produz tipicamente:

[altura, largura, 3]

Valores originais:

0 até 255

Exemplos:

preto = [0, 0, 0]
branco = [255, 255, 255]
vermelho = [255, 0, 0]


32. RESIZE BILINEAR
-------------------

resizeBilinear transforma a imagem em 640 x 640.

A interpolação bilinear considera pixels vizinhos e tende a ser mais suave que
nearest neighbor.

Limitação:

Uma imagem retangular redimensionada diretamente para um quadrado sofre
distorção.

Alternativa:

letterbox:

- preserva proporção;
- adiciona padding;
- remove o efeito do padding nas coordenadas finais.


33. NORMALIZAÇÃO
----------------

Fórmula:

pixel normalizado = pixel / 255

Exemplos:

0 -> 0
127,5 -> 0,5
255 -> 1

Faixa final:

[0, 1]

O pré-processamento deve ser compatível com aquele esperado pelo modelo.


34. TF.TIDY()
-------------

tf.tidy() envolve o pré-processamento.

Ele descarta intermediários:

- tensor inicial;
- redimensionado;
- dividido.

O tensor retornado sobrevive ao tidy e precisa de dispose depois.

Regra:

tidy cuida dos temporários internos;
dispose cuida do valor que saiu do tidy.


35. EXECUTEASYNC
----------------

runInference(tensor) chama:

output = await model.executeAsync(tensor)

Depois:

tf.dispose(tensor)

O código assume que as três primeiras saídas são:

1. boxes;
2. scores;
3. classes.

Promise.all lê os três tensores em paralelo:

boxes.data()
scores.data()
classes.data()

Depois todos os tensores de output são descartados.


36. TENSOR.DATA()
-----------------

Tensor é estrutura gerenciada pelo TensorFlow.js.

data() copia ou disponibiliza seus valores para JavaScript e retorna Promise.

Depois de:

boxesData = await boxes.data()

podemos descartar boxes e continuar usando boxesData.

Trade-off:

- necessário para pós-processar com JavaScript;
- pode causar sincronização e transferência GPU -> CPU;
- uso excessivo pode reduzir desempenho.


37. SAÍDAS DO MODELO
--------------------

BOXES

Coordenadas das caixas.

SCORES

Confiança de cada detecção.

CLASSES

Índice da classe de cada detecção.

O model.json declara quatro saídas de assinatura, mas o código aproveita as três
primeiras e descarta todas ao final.

Importante:

O significado e a ordem das saídas dependem da conversão do modelo. Ao trocar o
arquivo, devemos inspecionar model.outputs e shapes, em vez de assumir que a nova
versão segue a mesma ordem.


38. LIMIAR DE CONFIANÇA
-----------------------

Constante:

CLASS_THRESHOLD = 0.4

Regra:

se score < 0.4:
    ignorar

0.4 equivale a 40% na apresentação.

Threshold menor:

- mais detecções;
- mais falsos positivos.

Threshold maior:

- menos falsos positivos;
- risco de perder alvos.

O valor ideal deve ser medido.


39. FILTRO DE CLASSE
--------------------

Depois do score:

label = labels[classes[index]]

Se label não for kite, a previsão é ignorada.

O filtro evita atirar em outras classes.

Para aceitar bird e kite:

classes permitidas = [bird, kite]

Para um modelo customizado:

classe permitida = duck


40. BOUNDING BOX
----------------

O código pega quatro valores:

[x1, y1, x2, y2]

Interpretação:

x1, y1:
    canto inicial;

x2, y2:
    canto final.

Depois multiplica:

x por largura;
y por altura.

Isso pressupõe coordenadas normalizadas entre 0 e 1.

Ponto crítico:

Alguns modelos usam ordem [y1, x1, y2, x2]. Sempre confirmar a assinatura e uma
imagem de teste. Inverter a ordem desloca a mira.


41. CONVERSÃO PARA PIXELS
-------------------------

Se a caixa é normalizada:

xPixel = xNormalizado * largura
yPixel = yNormalizado * altura

Exemplo:

largura = 1000
x = 0,25

xPixel = 250

O Worker usa width e height do ImageBitmap original, não 640, porque a mira deve
voltar ao espaço da imagem capturada.


42. CENTRO DA CAIXA
-------------------

Fórmulas:

boxWidth = x2 - x1
boxHeight = y2 - y1

centerX = x1 + boxWidth / 2
centerY = y1 + boxHeight / 2

Forma equivalente:

centerX = (x1 + x2) / 2
centerY = (y1 + y2) / 2

Atirar no centro reduz o risco de mirar apenas na borda.


43. GENERATOR
-------------

processPrediction é function*.

Um generator usa yield.

Em vez de criar uma lista completa, ele entrega uma previsão por vez.

Consumo:

for (const prediction of processPrediction(...))

Vantagens didáticas:

- fluxo incremental;
- memória controlada;
- separação entre filtrar e enviar.

No volume pequeno dessa aula, um array também funcionaria. O generator ensina
uma forma elegante de produzir resultados sob demanda.


44. ENVIO DAS PREVISÕES
-----------------------

Para cada previsão aceita:

postMessage({
    type: prediction,
    x,
    y,
    score
})

O score é:

scores[index] * 100

e depois:

toFixed(2)

Consequência:

score vira string formatada, por exemplo:

87.42

Se precisarmos calcular com ele depois, é melhor manter número e formatar apenas
na View.


45. RECEBIMENTO NA THREAD PRINCIPAL
-----------------------------------

worker.onmessage recebe data.

Se type for prediction:

1. registra coordenadas no console;
2. atualiza o HUD;
3. torna a mira visível;
4. define posição;
5. obtém posição global;
6. chama game.handleClick().

O getGlobalPosition() é importante porque handleClick() espera coordenadas
globais, como um evento real do PixiJS.


46. MEMÓRIA E DISPOSE
---------------------

Tensores podem ocupar CPU, GPU ou WebGL.

O garbage collector do JavaScript não conhece sozinho todos os recursos internos
do TensorFlow.js.

Nesta aula:

- tf.tidy() descarta temporários;
- input é descartado depois de executeAsync();
- outputs são descartados depois de data();
- dummyInput é descartado.

Vazamento repetido cinco vezes por segundo cresce rapidamente.

tf.memory() ajuda a observar quantidade de tensores e bytes.


47. IMAGEMBITMAP E RECURSOS
---------------------------

Além dos tensores, ImageBitmap também merece atenção.

Depois de criar o tensor, uma evolução pode chamar close() no bitmap quando não
houver mais uso.

O objetivo é não manter recursos gráficos antigos enquanto novas capturas são
produzidas continuamente.

52. ERRO EM ASYNC FUNCTION
--------------------------

export default async function main(game) é JavaScript válido.

O erro Unexpected token function vinha do ESLint antigo.

Correções:

- ESLint 4.18.2 atualizado para 8.57.1;
- ecmaVersion 2022;
- sourceType module;
- ambientes browser, worker e node.

Cercas de Markdown pertencem à documentação. Se uma marca javascript com três
acentos graves for colada dentro de main.js, causará erro.

Causa:

62. BACKPRESSURE
----------------

Estratégia:

thread principal:
    se ocupado, não capturar;
    marcar ocupado;
    enviar frame;

Worker:
    inferir;
    responder;

thread principal:
    marcar livre.

Outra opção é manter apenas o frame mais recente.

Em tempo real, uma previsão atual vale mais que uma fila de previsões antigas.


63. MELHOR DETECÇÃO
-------------------

O código envia toda detecção aceita.

Se houver três alvos:

- três mensagens;
- três movimentos;
- possivelmente três tiros.

Critérios possíveis:

- maior score;
- maior caixa;
- mais perto do centro;
- alvo ainda não atingido;
- trajetória mais estável.

Fluxo:

filtrar -> ordenar -> escolher uma -> disparar


64. DETECÇÃO E RASTREAMENTO
---------------------------

Detecção:

Onde está o objeto neste frame?

Rastreamento:

É o mesmo objeto do frame anterior e para onde está indo?

Vantagens do rastreamento:

- menos inferências;
- mira suave;
- estimativa de velocidade;
- antecipação;
- evitar tiros repetidos.
